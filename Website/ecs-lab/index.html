THE BUILDING BLOCKS

三个概念，搭起一个游戏世界。

先问“它拥有哪些数据”，再问“哪些系统会处理它”。ECS 为游戏逻辑提供另一种组织方式。

E / 01

Entity · 实体

世界中某个事物的身份标识。角色、子弹、道具都可以是实体；身份本身无需承载玩法逻辑。

Entity #1042 → 一颗子弹
C / 02

Component · 组件

描述实体的数据。用位置、速度、伤害等组件组合出能力，避免让复杂的继承树决定所有行为。

Position { x, y } · Damage { value }
S / 03

System · 系统

查询需要的组件并执行逻辑。移动系统遍历拥有位置和速度的实体，按时间步更新位置。

Query(Position, Velocity) → Update

MAKE THE TRADE-OFF
选择 ECS，也要理解代价。
适合重点考虑的场景 ↗
  • 大量对象运行相似逻辑，例如弹幕、群体单位和粒子。
  • 玩法能力需要频繁组合，并希望减少深层继承。
  • 团队愿意明确划分模拟数据、系统依赖与表现层。
需要提前设计的部分
  • 性能依赖具体存储、访问模式和任务调度，ECS 不自动保证更快。
  • 原型存储中增删组件可能迁移实体，结构变化应避免无节制发生。
  • 编辑器工作流、调试、序列化与跨实体关系也需要配套方案。


KEEP EXPLORING
从理解架构，到开始实践。
ECS 和普通的组件式开发有什么区别？
组件式开发同样强调组合。典型 ECS 进一步区分实体身份、组件数据与系统逻辑，用查询选择批量处理的实体。仅仅给对象挂多个含行为的脚本，并不等于采用了这套组织方式。
什么是 Archetype（原型）？
在 Unity Entities 这类原型 ECS 中，同一组组件类型对应一个原型。拥有相同组件组合的实体会按此组织。为实体添加或移除组件会改变其原型；其他 ECS 实现也可能采用不同存储策略。
小型项目一定要用 ECS 吗？
无需为了架构而增加复杂度。先用实际对象数量、性能分析和玩法变化判断收益。也可以只把批量模拟部分交给 ECS，把界面与独特交互保留在其他结构中。
